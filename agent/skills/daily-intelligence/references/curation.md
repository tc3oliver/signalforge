# Curation — 什麼值得注意

讀者設定:在 AI / 軟體領域工作的技術人。看得懂 transformer 架構、會讀 release note、
自己跑 infra、對「某公司發表新 app」沒興趣,但對「某公司改了 API 定價結構」很有興趣。
他不需要你解釋什麼是 LLM,他需要知道**今天有什麼改變了他的判斷或工作**。

## 值得注意的三個條件

一則 item 至少要滿足其中一項才可能是 `CANDIDATE`:

1. **改變能力邊界** — 新模型/新技術做到了昨天做不到的事,或基準被明確推進。
2. **改變決策成本** — 定價、授權、API 相容性、停止支援、安全漏洞、法規。
   讀者可能因此要改架構、換供應商、排修補。
3. **改變趨勢方向** — 某個結構性變化第一次有實證(資金流向、人才流動、
   標準採納、重大開源專案轉授權)。

反過來說,**只是有人寫了一篇文章**不是條件。分析評論、教學、list-icle、
「五個你該知道的 X」、產品公關稿、募資新聞稿裡沒有數字的部分 — 都不是。

## 直接判 IRRELEVANT 的類型

- 消費性產品新聞(手機發表、遊戲、串流片單)。
- 純市場波動報導:「BTC 今日下跌 3%」「大盤收黑」— 沒有機制說明就是噪音。
  參見 `editorial-policy.md`。
- 教學、how-to、「入門指南」、觀點投書、個人心得。
- 名人動態、企業人事以外的八卦、法說會場邊花絮。
- 已經是舊聞的重貼(publishedAt 是今天但內容指涉幾週前的事件,且沒有新增)。
- 低訊噪比的社群抱怨,除非它本身構成事件(例如大量使用者同時回報某服務故障)。

## 便宜的分流:只看 title + summary

**預設不呼叫 `get_item_detail`。** title + summary 通常足以做到:

- 判掉噪音(上面那份清單)。
- 認出這是一則已知 cluster 的第 N 篇報導 → `DUPLICATE`,填 `storyId`。
- 認出這是新事件 → `CANDIDATE`。

只在下列情況花 detail:

| 情況 | 為什麼值得 |
|---|---|
| summary 只有標題重述、看不出發生什麼事 | 沒有 detail 無法判斷 |
| 疑似 cluster 的**主來源**,要確認事件細節與版本號 | 影響 canonicalTitle 與 factRefs |
| 兩則看起來可能同一事件,但實體/版本對不上 | 去重的關鍵證據在內文 |
| 要決定 `changeType` 卻不確定今天新增了什麼 | novelty 判斷需要具體事實 |
| 內含數字、需要確認是否有對應 structured fact | 避免憑空引數字 |

一個大略的比例:每 50 則 item,detail 呼叫控制在 10 次以內。
detail 花在主來源身上,不要花在第七篇轉述上。

## 批次紀律

- 一次 `list_unseen_items` 取一頁(上限 50),**這一頁全部判完**再抓下一頁。
- 判斷順序:先掃過整頁的 title,把明顯噪音一次判掉;
  剩下的才逐則處理,並在需要時 `search_items` 找兄弟。
- 整頁的 story 和整頁的判斷用**一次** `commit_curation_batch` 一起送出。
  每多一次呼叫,整頁都會再被送一次給模型。
- 每則 decision 的 `reason` 寫一句具體的話。不要寫「不相關」,
  寫「消費性產品發表,無技術或決策影響」。`reason` 是你下一輪回頭看的唯一線索。
- `DUPLICATE` 一定要帶 `storyId`,指向它所屬的 cluster。
  沒有 storyId 的 DUPLICATE 等於資訊丟失。
- `CANDIDATE` 也要帶 `storyId`(該 item 是這個 story 的成員)。
  `IRRELEVANT` 不需要 storyId。

## 一個常見錯誤

看到一頁 50 則裡有 30 則明顯是噪音,就只 record 那 20 則「有內容的」。
**錯。** 噪音也必須 record 成 `IRRELEVANT`,否則它們永遠停在 unseen,
`submit_materials` 會被拒。判掉噪音跟成案一樣是工作成果。
