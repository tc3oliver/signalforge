# 編輯方針

## Tier A / B / C

Curator 在 `submit_materials` 時給每則 story 一個 `tier`。
tier 是**給 Editor 的取捨建議**,不是分數的重複。

### Tier A — 今天不看會出事
讀者今天就需要據此行動或調整判斷。典型:

- 他正在用的服務中斷、變更 API、宣布 EOL、改定價或授權。
- 影響廣泛的安全漏洞,尤其已有實際利用。
- 改變能力邊界的技術發布(新模型、新架構、重大效能突破)。
- 會改變產業結構的併購、監管裁決、法規生效。

A 通常 3–5 則。超過 6 則代表你的門檻太鬆。

### Tier B — 值得知道,但不急
方向性的、需要幾週才會發酵的。典型:

- 重要但非緊急的版本發布、值得追蹤的研究成果。
- 進行中的爭議、尚未定案的監管動作。
- 明顯的趨勢證據,但單則影響有限。

B 是簡報的主體,通常 5–9 則。

### Tier C — 記錄在案
放進 materials 讓 ledger 有歷史,但 Editor 多半不會寫進簡報。典型:

- `NO_MATERIAL_CHANGE` 的持續性 story。
- 小幅度的例行更新。
- 值得留一筆以便明天比對的低訊號事件。

C 進 materials,不一定進 brief。

## 什麼進得了最終簡報

Editor 從 materials 裡挑 8–15 則寫成 brief,其中 3–5 則標 `mustKnow: true`。

進得了的條件,任一:

- 讀者**可能需要因此改變做法**(換掉某個依賴、排一個修補、重新評估某個供應商)。
- 讀者**對世界的模型會被更新**(某個他以為做不到的事現在做得到了)。
- 它是**一條他在追蹤的線的新節點**(有 ledger 歷史、今天有實質進展)。

進不了的:

- `NO_MATERIAL_CHANGE` 且沒有其他理由。
- 只有評論沒有事實的 story。
- 重要性撐不起一段文字的 — 如果 `whyItMatters` 只能寫出「這顯示產業持續發展」,
  它就不該在簡報裡。

## 趨勢證據 ≠ 可獨立刊登的 story

這是最容易造成**同一份情報價值被算兩次**的錯誤。

當你辨識出一條 emerging signal,它必然是由若干則 story 共同構成的。
那些構成事件(constituent events)當中,有一部分的編輯價值**幾乎全部來自
「它是這條趨勢的證據之一」** — 單獨拿出來看,它撐不起簡報裡有限的一個位置。

如果你把 signal 寫進去,又把它的每一則弱證據也各自寫成 final story,
讀者會在同一份簡報裡讀到同一件事兩次:一次是趨勢,一次是散落的細節。
簡報變長了,資訊量沒有增加,而真正重要的其他 story 被擠掉。

### 規則

> 一則 story 是某個重要趨勢的證據,**不因此自動具備獨立刊登資格**。
>
> 如果一則 story 的主要編輯價值來自「為某條 aggregate emerging signal 提供證據」,
> 它原則上應該**留在支撐證據的位置**(signal 的 `storyIds`),
> 而不是另外成為一則 final story。
>
> constituent story 只有在**不依賴那條 aggregate trend、自己就滿足一般刊登門檻**時,
> 才可以同時獨立刊登。

注意「原則上」與「只有在」的方向:預設是**不**獨立刊登,獨立刊登需要理由。

### Standalone Value Test

決定一則 constituent 要不要獨立成篇時,問這一句:

> **「如果那條 aggregate emerging signal 根本不存在,
> 這則事件還值得佔用今天簡報裡有限的一個 story 位置嗎?」**

- 答**不值得** → 它只是 supporting evidence。放進 signal 的 `storyIds`,不要寫成 final story。
- 答**值得** → **必須獨立刊登。** 它會**同時**是 final story 和 signal 的證據,這沒有問題。

### 這個測試只適用於「弱證據」

Standalone Value Test 是用來擋掉**本來就不夠格**的 story,不是用來壓縮篇幅的工具。

- 它**只**適用於某條 emerging signal 的構成事件。
- 不是 signal 構成事件的 story,完全不受它影響,照常用一般刊登門檻判斷。
- 一則 story 被 signal 引用,**不會降低**它自己的刊登資格。夠格就是夠格。

**被 signal 引用不是扣分項。** 如果一則事件本身就滿足刊登門檻 —— 讀者會因此改變做法、
世界模型被更新、或它是追蹤中的線的新節點 —— 那它就該出現在 `stories` 裡,
即使它同時是某條趨勢的證據。把這種 story 降級成純證據是**漏報**,比多寫一則邊際 story 嚴重得多。

### 不確定時,刊登

這份簡報的失敗模式不對稱:

- 多寫一則邊際 story → 讀者多花二十秒。
- 漏掉一則他需要知道的事 → 他從別處才發現,而且是在已經來不及的時候。

所以 Standalone Value Test 答不出明確的「不值得」時,預設是**刊登**。
只有當你能具體說出「這則單獨看撐不起一段文字」時才把它留在證據位置。

### 篇幅的實際落點

`stories` 的合法範圍是 8–15,但 8 是下限不是目標。
正常的一天大約 **10–13 則**。如果你只寫到 8 或 9,回頭檢查一次:
是不是有夠格的 story 被 Standalone Value Test 誤殺了?

判斷「值得」的依據就是上一節那三個條件(改變做法 / 更新世界模型 / 追蹤中的線有新節點),
而且必須在**不提那條趨勢**的情況下說得通。
一個實用的檢查:試著只用這則事件本身寫出 `whyItMatters`。
如果寫出來的句子非得提到「這反映了某某趨勢」才站得住,答案就是不值得。

### 要避免的形狀

```
emergingSignals: [ 一條強訊號 ]
stories: [ 弱證據 A, 弱證據 B, 弱證據 C, ... ]   ← 同一份情報價值被重複計算
```

應該長成:

```
emergingSignals: [ 一條強訊號,storyIds 指向 A B C D ]
stories: [ ...其他真正獨立成立的 story... ]
        ( A B C D 之中若有哪一則獨立門檻也過得了,它才出現在這裡 )
```

signal 的 `storyIds` 指向的 storyId 必須存在於 materials / ledger 中 —
這不代表它們每一則都要成為 brief 的 final story。兩者是不同的集合。

### Worked example

某天出現這些彼此不相關的事件:

- 某地區的電力公司宣布一組新的大型用電併網申請排隊時間延長
- 某資料中心營運商發布季度報告,提到冷卻系統交期拉長
- 某工程承包商的財報顯示特定型號變壓器訂單積壓
- 某地方政府對新建資料中心的用水核可程序增加一道審查

四則單獨看都是小事:交期、排隊、積壓、行政流程。
任何一則都不會改變讀者明天的做法,也不會更新他對世界的模型。

但四則並排,浮現的是**算力擴張正在撞上實體基礎設施的硬約束** —
這是值得寫的 emerging signal。

正確的處理:

- `emergingSignals` 收這條訊號,`storyIds` 指向這四則。
- 這四則當中,通不過 Standalone Value Test 的留在證據位置,不另外成為 final story。

注意這裡的判斷是**逐則**做的,不是整組一起丟掉。四則裡若有一則自己就夠格,它照樣刊登。

例外:如果其中「用水核可增加審查」那則,其實是一項**已生效的新規**,
明確改變了某類專案的可行性 — 那它在不提趨勢的情況下也站得住,
可以獨立刊登,同時仍然是 signal 的證據。

## `mustKnow` 的門檻

`mustKnow: true` 是 3–5 則,意思是「如果讀者只讀三十秒,就讀這幾則」。
全部 Tier A 不一定都要 mustKnow;mustKnow 也不必然全來自 A,
但一則 C 被標 mustKnow 需要在 `whyItMatters` 裡說得通。

## Section 分類

`section` 的合法值(verbatim):
`MUST_KNOW`、`AI_LLM`、`DEVELOPER_OSS`、`RESEARCH`、`CRYPTO_MARKET`、`MACRO`、`COMPANIES`。

| Section | 收什麼 |
|---|---|
| `MUST_KNOW` | 當日最關鍵的幾則。與 `mustKnow: true` 搭配使用 |
| `AI_LLM` | 模型發布、推論/訓練基礎建設、AI 產品與 API、AI 政策 |
| `DEVELOPER_OSS` | 開源專案、語言與框架、開發工具、授權、套件生態、安全漏洞 |
| `RESEARCH` | 論文、實驗結果、學術界動態。偏「還沒落地」的一端 |
| `CRYPTO_MARKET` | 鏈上事件、協議升級、交易所與監管、有機制可說的價格事件 |
| `MACRO` | 利率、通膨、就業、貿易與產業政策、供應鏈 |
| `COMPANIES` | 併購、財報中的結構性訊號、人事與組織變動、商業模式轉向 |

### 歸類原則

- **一則 story 只有一個 section。** 選讀者最可能去找它的那一個。
- 邊界情況用「這件事的驅動力是什麼」判斷:
  - 某 AI 公司募資 → `COMPANIES`(商業事件),不是 `AI_LLM`。
  - 某 AI 公司發模型 → `AI_LLM`。
  - 某 AI 框架的授權變更 → `DEVELOPER_OSS`(影響的是使用者的合規),不是 `AI_LLM`。
  - 某論文被產品化落地 → `AI_LLM`;還停在論文階段 → `RESEARCH`。
  - 晶片出口管制 → `MACRO`(政策驅動),即使它影響 AI。

### 空的 section 直接省略

**沒有實質內容的 section 就不寫,絕不填充。**

今天沒有值得寫的 macro 事件 → brief 裡就沒有 MACRO 的 story。
不要為了「版面完整」去把一則 Tier C 的例行數據拉上來充數。
一份七個 section 都有內容的簡報,如果其中三個是湊的,比四個 section 的簡報更糟 —
它訓練讀者忽略你的分類。

同理,不要把一則 story 硬塞到冷清的 section 讓它「看起來平均」。

## 明確排除

### 例行市場波動
「BTC 今日下跌 4%」、「那斯達克收黑」、「油價微升」— **不是 story**。

除非:
- 有明確的**機制**可說(某個協議被攻擊導致拋售、某央行決議造成的反應),且
- 幅度或性質是**結構性**的(不是日常區間內的擺盪)。

寫進去的時候,重點是機制不是數字。數字走 `factRefs`。

### 消費性新聞
手機、家電、遊戲、串流內容、消費性訂閱方案。讀者不是在這個身分下讀這份簡報。
例外:當它揭露了技術或商業結構的變化(例如某裝置上市代表某個晶片量產了)。

### 其他排除
- 純觀點與評論文,沒有新事實。
- 教學、教程、工具推薦清單。
- 公關稿裡沒有可查證內容的部分。
- 尚未發生的預告(「下週將發布」)— 除非預告本身改變了什麼(例如 EOL 日期公布)。

## Emerging signals 與 watchNext

- `emergingSignals`:見 `emerging-signals.md`。寧缺勿濫,0–3 條。
- `watchNext`:至少 1 條。寫**具體可驗證的觀察點**,不是「持續關注 AI 發展」。
  好的寫法:「X 公司是否在本週內對 Y 指控做出正式回應」、
  「該漏洞的 patch 是否涵蓋 3.x 分支」。
- `dailyAnalysis`:把當天幾則 story 串起來的判斷,不是摘要的摘要。
  如果它只是把上面的標題再列一次,就沒有存在價值。
